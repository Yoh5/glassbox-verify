# glassbox-verify

A second opinion on a [Glass Box](https://github.com/Yoh5/glassbox) ledger,
written in Rust and sharing no line of code with the tool that wrote it.

```
glassbox-verify ledger.jsonl
```

```text
runs/escalation/ledger.jsonl : INTACT — 12 enregistrement(s) re-chaîné(s), aucun écart.
```

```text
captures/altere.jsonl : ROMPU — 12 enregistrement(s) lu(s), 1 problème(s) :
    enregistrement 7 (answer) porte severity — qu'aucune empreinte ne couvre :
    ce vérificateur ne peut pas se porter garant d'un champ qu'il ne connaît pas
```

## Why a second verifier

Glass Box says *"don't believe me, re-run it."* Until now, re-running meant
executing the code of the person who wrote the ledger. If their hash function
has a flaw, their verifier has the same one, and the two agree on a wrong
answer. Agreement between a program and itself is not evidence.

This binary reads the specification and reimplements it:

```
chain = "sha256:" + sha256(prev + json.dumps(body,
            sort_keys=True, separators=(",", ":"), ensure_ascii=False))
```

over nine named fields. When the two implementations agree, the agreement
means something.

## What the reimplementation actually cost

Almost all of it is float formatting.

A real ledger holds `2.676e-05` and `6.659999999999999e-05`. Rust prints
`0.00002676` with `{}` and `2.676e-5` with `{:e}` — three renderings, one
correct byte sequence. One byte of difference and an intact ledger is declared
forged.

Python's rules were **read off the interpreter**, not assumed:

| value | Python writes |
|---|---|
| `1e15` | `1000000000000000.0` |
| `1e16` | `1e+16` |
| `1e-4` | `0.0001` |
| `1e-5` | `1e-05` |
| `1e100` | `1e+100` |

Scientific notation when the decimal exponent is **≥ 16 or ≤ −5**; a signed
exponent of **at least two digits**; `.0` appended to integral floats.

`tests/conformite.json` freezes this: 19 canonical forms and 3 real chained
records, generated by Glass Box's own Python. If Python ever changes its
formatting, the test fails instead of letting this binary validate wrong
hashes.

## Agreement, measured

Both verifiers, same four files, same verdicts:

| file | Rust | Python |
|---|---|---|
| `ledger.jsonl` (intact) | intact, 12 records | intact |
| `altere.jsonl` (field added) | record 7 carries `severity` | record 7 carries `severity` |
| one value edited | record 5 edited since written | record 5 has been edited |
| one record deleted | record 7 does not follow | record 7 does not follow |

The edited value was `2.856e-05 → 5.712e-05` — the exact float shape that
would have broken a naive reimplementation, and it did not.

## No dependencies

`Cargo.toml` lists none, and that is the argument rather than a boast. This
exists so an auditor can check a ledger without trusting whoever wrote it; a
self-contained executable is a promise you can keep, while a dependency tree —
however good — is one more thing to audit.

SHA-256 is implemented here. That is not "rolling your own crypto": it is a
published algorithm, frozen since 2001, with official test vectors, and the
tests check against them. Designing a *new* algorithm would be the mistake.
This one has no key, no seed and no secret.

## Build and test

```bash
cargo test            # vectors, conformance corpus, real chained records
cargo build --release # 240 kB, one file
```

## What it does not do

It does not resolve evidence citations — that needs the evidence store, not
just the ledger. Glass Box's own verifier does, and this one says so rather
than implying a ledger is fully checked when it is not.
